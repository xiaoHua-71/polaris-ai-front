## 1.1 目标

把现有单轮聊天页升级为**多轮对话**。后端已经用 MySQL 保存记忆，前端只需要：

1. 维护一个稳定的 `conversationId`（规则见 [2-会话ID规则](2-会话ID规则.md)）；
2. 每次 `POST /api/chat` 都带上它；
3. 提供「新会话」入口，换 ID 并清空当前消息。

**非目标**（本次不做）：SSE 流式、历史消息查询接口、Markdown 渲染、鉴权 / 多用户、工具调用、RAG。

> M3 的流式对接单独成文，见 [5-流式对接](5-流式对接.md)；先完成本文档组的 M2 改造。

## 1.3 `POST /api/chat`

请求：

```json
{
  "message": "我叫 Alice，请记住",
  "conversationId": "0f8fad5b-d9cb-469f-a165-70867728950e"
}
```

响应（HTTP 200）：

```json
{
  "content": "好的，Alice，我记住了。"
}
```

字段约束：

| 字段 | 必填 | 规则 |
|---|---|---|
| `message` | 是 | 非空白字符串；前端先 `trim()`，空则不发请求 |
| `conversationId` | 是 | 非空字符串，长度 ≤ 64；推荐 UUID（36 字符） |

错误：

| 场景 | HTTP | 响应体 |
|---|---|---|
| `message` 空 | 400 | Spring 默认错误体；**不含具体原因** |
| `conversationId` 空 / 超长 | 400 | 同上 |
| 模型调用或数据库异常 | 500 | Spring 默认错误体；具体原因只在后端日志 |

前端对 4xx/5xx 统一展示现有 `ApiError.message` 即可，不要尝试从响应体提取业务原因。

## 1.4 curl 自测

```bash
printf '{"message":"我叫 Alice，请记住","conversationId":"11111111-1111-1111-1111-111111111111"}' > /tmp/chat-1.json
curl -X POST http://localhost:8103/api/chat \
  -H 'Content-Type: application/json' \
  --data-binary @/tmp/chat-1.json

printf '{"message":"我叫什么？","conversationId":"11111111-1111-1111-1111-111111111111"}' > /tmp/chat-2.json
curl -X POST http://localhost:8103/api/chat \
  -H 'Content-Type: application/json' \
  --data-binary @/tmp/chat-2.json
# 第二次应回答 Alice
```

> 中文请求体写 UTF-8 文件再用 `--data-binary`，避免 Windows 终端 GBK 编码问题。
